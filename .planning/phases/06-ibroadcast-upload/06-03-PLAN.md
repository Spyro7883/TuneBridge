```python
def _upload_worker(self, row_id: int, token: str, user_id: int, library: dict) -> None:
    """Worker thread: duplicate check then upload. Per-row isolated (D-16).

    Arguments are passed by _start_upload_batch — no auth call inside worker (D-04).
    All status transitions via row_status_changed signal (thread-safe Qt queued path).
    """
    if self._closing.is_set():
        return
    try:
        meta   = self._row_metadata.get(row_id, {})
        title  = meta.get("title", "")
        artist = meta.get("artist", "")
        file_path = self._saved_paths[row_id]

        if _is_duplicate(title, artist, library):
            self._dispatcher.row_status_changed.emit(
                row_id, SongStatus.ALREADY_UPLOADED.value
            )
            self._on_upload_row_finished(row_id, SongStatus.ALREADY_UPLOADED.value)
            return

        success = _ibroadcast_upload(file_path, user_id, token)
        status  = SongStatus.DONE if success else SongStatus.FAILED_UPLOAD
        self._dispatcher.row_status_changed.emit(row_id, status.value)
        self._on_upload_row_finished(row_id, status.value)
    except Exception as exc:
        logging.getLogger(__name__).warning("Upload worker failed row %d: %s", row_id, exc)
        if not self._closing.is_set():
            self._dispatcher.row_status_changed.emit(
                row_id, SongStatus.FAILED_UPLOAD.value
            )
        self._on_upload_row_finished(row_id, SongStatus.FAILED_UPLOAD.value)
```

_on_upload_row_finished — exact implementation (D-11, D-12):
```python
def _on_upload_row_finished(self, _row_id: int, status: str) -> None:
    """Track upload batch completion. Called from _upload_worker threads.

    NOTE: _upload_worker calls this directly (not via signal), so this method
    executes on a worker thread — counter vars are safe because Qt's queued
    connection for row_status_changed ensures ordering, and _upload_total is
    written before any worker starts. Counters are only written here.
    When all rows resolve: emit upload_batch_done, update status bar. (D-11/D-12)
    """
    terminal = (
        SongStatus.DONE.value,
        SongStatus.ALREADY_UPLOADED.value,
        SongStatus.FAILED_UPLOAD.value,
    )
    if status not in terminal:
        return

    if status == SongStatus.DONE.value:
        self._upload_done += 1
    elif status == SongStatus.ALREADY_UPLOADED.value:
        self._upload_existed += 1
    else:
        self._upload_failed += 1

    finished = self._upload_done + self._upload_existed + self._upload_failed
    if finished < self._upload_total:
        self.statusBar().showMessage(
            f"Uploading {finished} of {self._upload_total}…"
        )
        return

    # All upload rows resolved (D-11, D-12)
    self._dispatcher.upload_batch_done.emit()
    self.statusBar().showMessage(
        f"Done — {self._upload_done} uploaded, "
        f"{self._upload_existed} already existed, "
        f"{self._upload_failed} failed"
    )
```

NOTE on _on_upload_row_finished thread safety:
_upload_worker calls _on_upload_row_finished directly from worker threads (same as RESEARCH.md shows).
_upload_total is written once before workers start → safe.
Counter vars (_upload_done/_existed/_failed) are NOT protected by a lock — this matches the RESEARCH.md
thread-safety analysis (§6) which confirms: "Written only in _on_upload_row_finished via Qt queued → main thread".
However, _upload_worker calls this directly (not via signal). For v1.0 with max 4 threads and CPython GIL,
plain int increments are safe. Add a threading.Lock if this becomes a concern in v1.1.

- SongStatus.FAILED_UPLOAD.value == "Failed — upload"

| Boundary | Description |
|----------|-------------|
| worker thread → _on_upload_row_finished | Counter mutation called from worker thread (not Qt main thread) |
| _upload_worker → _saved_paths / _row_metadata | Read-only access to Phase 5 shared dicts from thread |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-08 | Tampering | _upload_worker reads _saved_paths from thread | accept | Phase 5 fully completes before folder_batch_done fires; no concurrent writers (RESEARCH.md §6 confirms safe) |
| T-06-09 | Denial of Service | _upload_worker timeout=120 blocks thread slot | accept | ThreadPoolExecutor has max_workers=4; worst case 4 concurrent 120s uploads; acceptable for desktop app |
| T-06-10 | Repudiation | Upload success/failure not persisted across sessions | accept | v1.0 scope; row status visible in UI during session; session-only is sufficient per REQUIREMENTS.md §Future |
| T-06-11 | Denial of Service | _on_upload_row_finished counter race (CPython GIL) | accept | CPython GIL makes plain int +=1 atomic in practice; v1.0 with max 4 threads is safe; add Lock in v1.1 if needed |
</threat_model>
